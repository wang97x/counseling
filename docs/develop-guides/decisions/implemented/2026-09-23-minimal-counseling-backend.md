# 最小心理辅导业务后端

状态：implemented
类型：architecture
Owner：backend/counseling/src/counseling/storage/models.py

## 问题

现有业务后端已能维护最小学生档案，并正在建立文件记录的摘要与确认归档链路，但还不能完成一次不依赖 AI 的手工咨询记录、人工风险更新、追加更正和业务管理员最小统计闭环。若按预约、测评、危机工单、协作输入和数据仓库分别建设，会在首版引入多个尚无当前消费者的状态机，也会延后最基本的档案使用路径。

## 决策

- 继续使用 FastAPI、独立 `counseling` Python 包、PostgreSQL 和 MinIO 组成模块化单体；不拆微服务，不让 Redis 拥有业务终态。
- 学生档案保存负责人、展示名、班级、生命周期状态和当前人工风险投影。业务管理员只读取本部门最小元数据与聚合数量，不能读取背景、咨询正文和附件。
- 复用现有 `counseling_record_*` 表承载文件型和手工型咨询记录，以 `record_kind` 区分来源。草稿使用乐观版本和追加修订，人工确认在一个事务中创建不可变正式快照。
- 正式记录纠错通过引用原记录的追加更正保存，不开放正式记录更新或删除接口；数据库触发器同时保护正式记录和更正。
- 风险等级只由辅导员通过追加风险事件更新。新增事件、更新学生当前风险投影和写审计在一个事务中完成；系统不从记录文本或模型结果自动改变风险。
- 统一时间线合并手工咨询记录、文件型正式记录、追加更正、人工风险事件和既有档案会话。业务终态来自 PostgreSQL，不建立通用事件总线。
- AI 摘要继续位于可选生成端口后，只能产生草稿修订；手工记录闭环不依赖模型、worker 或知识库。

## 替代方案

- 为手工咨询记录另建一套平行草稿和正式记录表：可以避免修改现有表，但会复制版本、确认、权限、审计和时间线语义，因此拒绝。
- 引入通用表单或工作流引擎：可以覆盖未来测评和危机工单，但当前没有第二个稳定消费者，首版采用明确字段和线性状态。
- 把风险等级直接写在学生表而不保留事件：实现更少，但无法证明变更依据、操作者和历史，因此拒绝。
- 让业务管理员读取咨询正文以便统计：查询方便，但扩大敏感数据访问范围，因此只提供数据库聚合和最小元数据。

## 后果

- 统一记录表把文件来源字段改为可空；服务按 `record_kind` 校验，不能让文件记录缺少来源或手工记录伪造对象路径。
- `current_risk_level` 是查询投影而非独立临床结论；任何展示都必须能回到最近的人工风险事件，未评估不能解释为低风险。
- 旧文件型 P0 链路继续作为 P1 增强。本决定只拥有手工业务闭环，不宣称真实模型、MinIO 和浏览器验收已完成。
- 预约、测评、自动预警、完整危机工单、转介回访、协作输入和复杂看板不在本实现范围。
- 真实 PostgreSQL 已验证带旧会话行的 v1 到 v2、空库到 v2 和重复迁移。
